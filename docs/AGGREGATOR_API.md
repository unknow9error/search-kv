# API агрегатора ЖК Meken

Новый контракт `/v1/projects` дополняет существующий квартирный API. `/v1/search`, `/v1/apartments`, `/v1/favorites`, `/v1/conversations` и их SSE сохраняют прежнюю семантику. Все новые пользовательские маршруты используют существующую анонимную Bearer-сессию. По последующему разрешению пользователя расширение выложено в production 6 октября 2026 года: `https://194.238.43.134`.

## Предметная модель

ЖК имеет стабильный UUID от источника и внешнего ID, самостоятельную запись даже без квартир и происхождение `public_project` либо `observed_lots`. Разные источники автоматически не объединяются по имени. `provider` означает источник; `developer_name` — отдельно опубликованного застройщика.

Цена содержит `kind`, `amount_kzt`, `source_url`, `observed_at`. Допустимые виды: `published_starting_price`, `observed_listing_minimum`, `unknown`. Опубликованная цена ЖК и минимум цен наблюдавшихся лотов возвращаются раздельно. Отсутствие данных — `null`, а не нулевая цена. Просроченные сведения и ошибки импорта не доказывают продажу.

`ProjectInput` хранит core identity/location/source, `published_starting_price_kzt`, `stage`, `completion`, `finish`, `buildings`, `images`, `documents`, `layouts` как отдельно полученные публичные сведения. Поля необязательны, источники и время обязательны. Тип планировки не содержит выдуманной цены, этажа или наличия конкретного лота. Фотографии фасада не выводятся из изображения планировки квартиры.

`source_url` — фактический источник данных, в том числе публичный метод API. Для кнопки перехода используется `website_url`, когда он есть; `website_scope=project` означает страницу ЖК, `provider_catalog` — общий каталог источника. Сведения `bigville_id`/`bigville_name` передаются только при их публикации источником. Компактные карточки списка, карты, сравнения и избранного содержат одну опубликованную фотографию фасада/территории и счётчики материалов; полные материалы загружаются через деталь ЖК.

## Маршруты

| Маршрут | Назначение |
|---|---|
| `POST /v1/projects/search` | `criteria`, `limit` 1–100, `cursor`, `sort`; ответ `items`, `total`, `next_cursor`, `criteria`, `sort`, `unknown_coordinates_count` |
| `GET /v1/projects` | Короткая форма списка по `city`, `q`, `limit`, `cursor`, `sort` |
| `GET /v1/projects/facets` | Районы, опубликованные застройщики, стадии и ценовые режимы по фактическим данным |
| `POST /v1/projects/map` | Та же поисковая семантика с `bounds`; координаты и число объектов без координат явно разделены |
| `POST /v1/projects/compare` | 2–3 `project_ids`; структурированные проекты и одинаковые строки сравнения без победителя/LLM |
| `GET /v1/projects/favorites` | Избранные ЖК с текущей свежестью/неизвестными полями |
| `PUT /v1/projects/favorites/{project_id}` | Идемпотентное сохранение ЖК |
| `DELETE /v1/projects/favorites/{project_id}` | Удаление только собственного избранного |
| `GET /v1/projects/{project_id}` | ЖК, публичные материалы, корпуса, инфраструктура и типизированные цены |
| `GET /v1/projects/{project_id}/apartments` | Опубликованные конкретные лоты; не обещает полный остаток продаж |
| `GET /v1/projects/{project_id}/layouts` | Самостоятельные опубликованные типы планировок |
| `GET /v1/project-layouts/{layout_id}` | Планировка со своим источником и датой, без объявления наличия |
| `POST /v1/projects/{project_id}/refresh` | Ограниченное повторное чтение подключённого публичного источника; не подтверждение покупки/брони |
| `POST /v1/projects/conversations` | Проектный диалог, отдельные `criteria` и `client_conversation_id` |
| `GET /v1/projects/conversations` | История проектных подборов |
| `GET /v1/projects/conversations/{id}` | Сообщения и сохраняемые результаты проектного диалога |
| `DELETE /v1/projects/conversations/{id}` | Удаление собственного диалога с сохранением избранного |
| `POST /v1/projects/conversations/{id}/turns` | Идемпотентный `client_turn_id`, `message`, необязательные `criteria`, `selected_project_ids`; JSON ответ базового проектного помощника с фактами/источниками |
| `GET /v1/catalog/sources` | Подключённые источники, фактическое покрытие, происхождение/свежесть |
| `POST /v1/data-reports` | Собственное сообщение о неточности: `client_report_id`, `project_id`, `category`, `message`; сохранённая квитанция `received`, без обещания ответа/исправления |
| `GET /v1/data-reports` | Только собственные квитанции |

## Критерии поиска

`ProjectCriteria`: `city`, `q`, `districts`, `developer_names`, `provider_ids`, `price_mode`, `price_min`, `price_max`, `stages`, `completion_before`, `rooms`, `area_min`, `floor_min`, `floor_max`, `required_amenities`, `amenity_scope`, `amenity_radius_m`, `include_stale`, `bounds`.

`price_mode` — `published_starting_price` по умолчанию либо `observed_listing_minimum`. Строгие ограничения комнаты/площадь/этаж проверяются на одном и том же опубликованном лоте; минимальная цена однокомнатной не удовлетворяет запросу двухкомнатной. При отсутствии параметров лотов соответствие не выдумывается. Стадия сдачи берётся только из опубликованного факта, не из прошедшего срока.

`sort`: `price_asc`, `price_desc`, `name`, `observed_desc`. Cursor связан с полными критериями и сортировкой. Список и карта используют одинаковый отбор. Новые фильтры не передаются в старый `Preferences.budget_max`, который остаётся бюджетом конкретной квартиры.

## Разговор и совместимость

Проектный помощник первого расширения работает в явно обозначенном базовом режиме: выполняет структурированный поиск/сравнение, понимает ограниченный набор уточнений и просит задать нераспознанные условия через форму. Полноценное понимание произвольного RU/KZ текста и подключение платной модели здесь не утверждаются. Старый квартирный разговор и его SSE не превращаются в проектный.

Избранное, история, восстановление и удаление профиля используют одного пользователя. Новые private записи удаляются каскадно вместе с профилем. Новые функции объявляются capabilities; фронт не показывает неподдержанное действие на старом сервере.

Конкретные DTO и фактически включённые capabilities дополнительно проверяются по обновлённому `openapi.json` и интеграционным тестам. Примерные данные дизайна не импортируются в реальный каталог.

История проектного диалога возвращает до 30 сообщений, `has_more` и `next_before`; следующая страница запрашивается через `?before=<next_before>`. Исторические результаты сокращаются до компактных карточек; повтор POST с тем же `client_turn_id` возвращает первоначальный сохранённый ответ. Повтор создания диалога или сообщения о неточности с тем же клиентским ID и другим содержимым возвращает 409. Избранное и квитанции ограничены 200 записями на профиль, проектные диалоги — 100.

## Подключение 13 экранов

| Экран | Данные и действия backend |
|---|---|
| 1. Первый запуск | Прежний анонимный auth, `/v1/config`, `/v1/catalog/sources`; состояние онбординга хранит клиент |
| 2. Поиск | `/v1/config`, `/v1/projects/facets`, создание проектного диалога или прямой поиск |
| 3. Фильтры | Фактические facets и `ProjectCriteria` |
| 4. Результаты | `/v1/projects/search`, cursor/total/sort, проектное избранное |
| 5. Карта | `/v1/projects/map`, bounds и учёт неизвестных координат |
| 6. Разговор | Проектные conversations/turns, `mode=basic`, структурированные критерии и ссылки |
| 7. ЖК | Деталь ЖК, материалы, факты, layouts, apartments, refresh и внешний website URL |
| 8. Квартира / планировка | Прежняя деталь квартиры либо `/v1/project-layouts/{id}` с разными предметными моделями |
| 9. Сравнение | `/v1/projects/compare`, 2–3 UUID, строки с источниками и неизвестными значениями |
| 10. Избранное | Проектное favorites; прежние квартирные favorites сохраняют отдельный смысл |
| 11. История | Проектные conversations/history/delete, продолжение сохранённых условий |
| 12. Профиль / восстановление | Прежние me/recovery; новые private записи принадлежат тому же пользователю и каскадно удаляются |
| 13. Помощь / документы | Источники и покрытие, privacy/terms из config, собственные data-reports; FAQ хранит клиент |

Фронт проверяет capabilities: `project_catalog`, `project_map`, `project_comparison`, `project_favorites`, `project_layouts`, `project_conversations_basic`, `catalog_sources`, `data_reports`. Эти признаки описывают поддержку API, а не наличие всех полей в каждом ЖК.

Пример запроса для списка и карты:

```json
{
  "criteria": {"city": "Астана", "price_mode": "observed_listing_minimum"},
  "limit": 20,
  "sort": "observed_desc"
}
```

В этом режиме известная `display_price.kind` равна `observed_listing_minimum`. Для фильтра опубликованной цены ЖК клиент явно выбирает `published_starting_price`. Без ценовых ограничений объекты с неизвестной ценой остаются в выдаче; с ограничениями не проходят отбор.

## Источники и миграция

BI сохраняет самостоятельный публичный справочник ЖК до чтения страниц лотов. Сбой источника лотов не отменяет уже полученный справочник. Новый адаптер `kind=public_project_feed` читает фиксированный публичный HTTPS `<base_url>/projects` без токена, cookies и редиректов: JSON `{ "as_of": "...", "projects": [...] }`. Входные записи валидируются через `ProjectInput`; цены, фотографии, сроки и планировки добавляются только при явной публикации этих полей. Этот адаптер реализован и проверен на контролируемом HTTP; дополнительные внешние каталоги не подключены автоматически.

Миграция `0009_project_catalog` следует за `0008_account_recovery`, добавляет отдельные projects/layouts/favorites/conversations/turns/data_reports. Старые квартирные таблицы и ответы сохраняются. Стартовая проекция старых публичных лотов в ЖК идемпотентна, не меняет дату наблюдения и не выводит общую отделку/срок ЖК из отдельного лота. Downgrade удаляет новые таблицы и их данные; старые записи сохраняются.

## Проверка 5 октября 2026

- Полный набор backend: **170 passed, 3 skipped** на SQLite; Ruff и проверка пробелов прошли. Два skip относятся к PostgreSQL-specific проверкам восстановления/retention, один — к отдельному Redis.
- Новый каталог/API и совместимость прежних auth/chat/catalog/recovery/OpenAPI: **82 passed** на отдельном реальном PostgreSQL 18.1, включая две пропущенные на SQLite проверки. Redis integration в этом запуске не проверялся.
- На отдельной PostgreSQL БД выполнены `0008 → 0009 → 0008 → 0009`, две проверки `alembic check`, сравнение старых записей и каскады удаления новых private данных. Отчёт локальной репетиции: `/private/tmp/meken-project-pg-migration-rehearsal-report.json`.
- Прямое чтение публичного BI: **56 ЖК Астаны и одна страница 150 лотов**. Это частичная выборка лотов; опубликованной цены ЖК «от» источник не дал. В данной выборке минимум цены лотов известен для двух ЖК. Каталог, карта, facets, источник, деталь, layouts/lots, сравнение, избранное, сообщение о неточности и удаление временного профиля проверены через ASGI; health/config/search — также через настоящий локальный HTTP.
- Для интеграции фронта 5 октября был запущен отдельный локальный API `http://127.0.0.1:8002` с этой публичной выборкой; Android emulator использовал `http://10.0.2.2:8002`. Сервер использовал временную SQLite; `.env`, production и платная модель в этих локальных проверках не использовались.

## Production проверка 6 октября

Backend обновлён, рабочая схема `0009_project_catalog`. Перед переключением свежая production-копия восстановлена и проверена на PostgreSQL 17; новый API под `meken_app` и совместимый rollback runtime прошли репетицию. HTTPS config объявляет все перечисленные project capabilities; поиск/карта/детали/layouts/lots/facets/sources/сравнение/favorites/basic conversation/history/data-reports и legacy apartment reads проверены. В данном live прогоне: Астана — 58 ЖК, карта — 57; временный профиль и private записи проверки удалены. [Развёртывание и backup границы](DEPLOYMENT.md).

Покрытие новых застройщиков и фактические материалы зависят от подключения их публичных источников. Проектный разговор остаётся базовым, JSON; старый квартирный SSE доступен по прежнему контракту. ИИ на production выключен.
